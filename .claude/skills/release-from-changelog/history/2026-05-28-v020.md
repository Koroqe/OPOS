# release-from-changelog run — v0.2.0 first real invocation

## Context

First production use of the new `release-from-changelog` skill. Cut v0.2.0 of OPOS itself, using the skill to extract the CHANGELOG section and run `gh release create`.

## Inputs

- `version`: `v0.2.0`
- `target_branch`: `feat/company-os-framework`
- `repo`: `Koroqe/OPOS` (from `.claude/task-tracking.config.json`)

## What happened

1. Verified CHANGELOG entry exists: `grep -F "## [0.2.0]" CHANGELOG.md` matched.
2. Extracted via canonical awk pattern (`p=1;print;next` + three stop clauses): 31 lines captured to `/tmp/release-notes-v0.2.0.md`.
3. Verified extract non-empty: `test -s` passed.
4. Verified no existing release with inverted-exit-code logic: `if gh release view v0.2.0; then abort; fi` correctly did NOT abort (no existing v0.2.0 release).
5. Auto-derived title from first `### ` subheading: produced `v0.2.0 — Added` (the literal section header — not ideal; see proposed_delta).
6. `gh release create v0.2.0 --repo Koroqe/OPOS --title "v0.2.0 — Added" --notes-file /tmp/release-notes-v0.2.0.md --target feat/company-os-framework` → returned `https://github.com/Koroqe/OPOS/releases/tag/v0.2.0`.
7. Verified creation: `gh release view v0.2.0 --json tagName --jq '.tagName'` returned `v0.2.0`.
8. **Manual post-step:** `gh release edit v0.2.0 --title "v0.2.0 — new skills + research-derived improvements"` to fix the auto-derived title.

## Outcome

`success` — all six PROCESS.md success_criteria satisfied. The skill replaced the multi-step manual workflow that had to be done by hand for v0.1.0 and v0.1.1 releases. Title-derivation bug surfaced as a follow-up; manual `gh release edit` workaround is acceptable.

## Notes

- Self-test against the framework's own release (dogfooding) is the strongest possible test — if the skill fails here, the framework can't ship its own releases.
- Title derivation is the only rough edge; everything else worked first time.
