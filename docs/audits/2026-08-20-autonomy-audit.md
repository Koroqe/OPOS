# OPOS autonomy audit — shared brief (read this first)

## What OPOS is

An open-source "company OS" Copier template (`Koroqe/OPOS`, upstream clone at `/Users/aleksei/Documents/Projects.nosync/OPOS`) that companies scaffold into their own repo and operate via Claude Code: agents in `.claude/agents/`, processes as skills (`.claude/skills/<name>/SKILL.md` + `PROCESS.md` + `history/` run records), departments under `departments/`, scheduling via cron routines with a declared-authority model, and (since v0.9.0/v0.9.1) a bidirectional self-improvement loop: `auto-sync` (autonomous pull of upstream releases), `review-history` (weekly triage of `proposed_delta` run-record entries), `propose-to-core` (anonymized upstream PRs behind a fail-closed redaction gate + `redaction-reviewer` agent). The reference consumer is Restaba at `/Users/aleksei/Documents/Projects.nosync/Restaba` (read-only evidence; do not modify either repo).

## The founder's two targets (audit against THESE, verbatim intent)

**Target 1 — Self-improving at the DERIVATION level.** The loop must not merely fix specific broken files. When a consumer's *derived* artifact (an agent, process, or department the consumer built inside their company) makes a mistake, the question is: HOW was it derived, and WHY did the derivation permit the mistake? The fix belongs in the generative machinery OPOS owns — the design skills (`design-process`, `design-agent`, `design-department`, `design-subdept`), `allocate-resource`, the templates in `shared/templates/`, the review/verification conventions — so the mistake CLASS is prevented for every company. Consumer-specific artifacts stay private; the *derivation lesson* travels upstream.

**Target 2 — Self-BUILDING departments.** The boilerplate departments are a core, not a toolset: OPOS's job is the way departments build themselves. Departments must act not as task executors but as builders of (a) their own processes, (b) knowledge about those processes, and (c) their RESOURCES — the tools, access, and capabilities needed to execute any task. Concretely: no operator of a consumer OPOS should ever have to think about which subagents or processes need to exist — the system must detect the gap and build them. Resource acquisition is first-class: e.g. the founder's Chrome browser with logged-in work accounts (Cloudflare, domains, email, any SaaS) is a declared tool agents may drive via CDP to execute tasks end-to-end; agents must TRY the available tooling first and escalate to the human only on failure, as a delegation of last resort. The near-term goal: consumer companies run as autonomously as possible, with updates and improvements flowing without the founder's or the framework maintainer's direct management. This precedes a public launch: few consumers today, so the machinery must hold without hand-holding as the ecosystem grows.

### Findings

The upstream repo's only workflow is `sync-opos.yml` (the consumer-shipped file); no PR CI exists at all. The framework repo carries the full 13-agent + 23-skill roster (it IS structurally an OPOS instance minus `.copier-answers.yml`), so maintainer tasks CAN become OPOS processes — `schedule-process` doesn't require `.copier-answers.yml` (only `review-history` and `auto-sync` do). 3. **[CRITICAL] Cross-consumer dedupe exists but is file-slug-granular and permanently lossy — two consumers' *different* fixes to the same file collapse into one, and the loser is suppressed forever.** Correcting the audit premise: `propose-to-core` step 3 DOES dedupe across consumers — `gh pr list --repo <upstream> --state all --limit 200` with local `[opos-core] <file-slug>` title matching is fleet-wide, not per-consumer. 1. OPOS's self-improvement loop is real but session-gated and leaf-targeted: it fixes the file that misbehaved, only while the founder's laptop is open, and never the generator that produced it — the opposite of both founder targets.
